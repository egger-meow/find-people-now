## 1. 整體導覽結構

```
底部導覽（4 個主 tab）
├─ 首頁（配對頁）
├─ 我的活動（進行中 / 已結束 兩個分頁）
├─ 通知
└─ 我的（個人資料 / 設定 / 帳號刪除 / 反饋QA）

突發性彈窗（不在導覽列，由通知或狀態變化觸發跳出）
├─ 小人數安全確認（PENDING_CONFIRMATION）
├─ 人數調整同意（Downgrade）
└─ 完成確認 + 再約（兩步）
```

## 2. 配對頁（首頁）

### 2.1 填表流程

| 步驟 | 內容 | 資料來源 |
|---|---|---|
| 1. 選活動類型 | 官方預設類型（含「先聚了再說」）+ 使用者提案通過的類型 | `GET activity_type?status=eq.APPROVED` |
| 2. 選時段 | 🔴 尚未細化，見第 7 節 | 前端算好傳 `earliest_start`/`latest_start` |
| 3. 選校區 | MVP 階段每校僅一個校區（NYCU=光復、NTHU=校本部），選單實質上是自動帶入 | 該校 `location` 表 distinct `campus` |
| 4. 選人數 | 依 `group_size_step` 動態生成離散（如籃球 6/8/10/12）或連續區間（如咖啡 2-4）選項 | `activity_type.default_min/max_participants`、`group_size_step` |
| 5. 人數調整開關 | 「人數不夠時，接受少一點人也算成局」切換 → 對應 `allow_downgrade` 參數 | 使用者可勾選 |
| 6. 送出 | `create_request` → `submit_request` | 成功後進入等待室 |

**移除「?」說明按鈕**：活動類型若有 `description`（如「先聚了再說」），改為卡片下方常駐顯示的一行小字副標題，不需要額外點擊互動。清楚易懂的類型（籃球、咖啡等）不顯示副標。

### 2.2 送出前預先攔截

- 使用者已有 `REQUESTING` 或 `MATCHED`/`ONGOING` 中的活動 → 一進配對頁直接導去該活動，不重新顯示表單
- 使用者可信度為 `New` → 人數選單中 ≤2 人的選項直接 disable，附提示文字，不等送出才顯示 `NEW_USER_LOW_HEADCOUNT` 錯誤

## 3. 等待室（`REQUESTING` 狀態）

- 目前房間成員頭像列（`request_member`）
- 「邀請朋友」按鈕：`get_or_create_invite_link` 產生連結、可分享、可撤銷（`revoke_invite_link`）
- 非發起人可「退出房間」（`leave_request`）；發起人可「取消整個配對」（`cancel_request`）
- 距離 `latest_start` 的倒數

**技術要求**：此畫面必須用 **Supabase Realtime** 訂閱 `match_request` 狀態變化，不能只靠靜態載入或使用者手動刷新——配對成功、進入 `PENDING_CONFIRMATION`、或逾時 `EXPIRED` 都是伺服器背景排程主動觸發的狀態變化，需要即時反應並跳轉。

**刻意設計，非漏做**：等待室不提供編輯已送出 Request 的活動類型/時段/人數等核心欄位的功能。發起人決定這次要做什麼，受邀者只有加入或不加入的選擇權。理由：① Request 送出後隨時可能已被 Matching Engine 列為候選對象，臨時編輯核心欄位會製造競態風險；② 若想法真的不同，重新建立一個新 Request 成本很低，不需要為此換取編輯功能的複雜度。

## 4. 我的活動（依狀態動態切換內容）

| 狀態 | 顯示位置 | 內容 |
|---|---|---|
| `REQUESTING` | 進行中 | 等待室（見第 3 節） |
| `PENDING_CONFIRMATION` | 進行中 | 「等待確認中」卡片，點入跳出彈窗（見第 6.1 節） |
| `MATCHED` / `ONGOING` | 進行中 | 兩個分頁籤（見 4.1） |
| `COMPLETED` | 已結束 | 完成確認彈窗（若未填）、再約按鈕、活動摘要 |
| `EXPIRED` / `CANCELLED` | 已結束 | 簡短顯示「未成局」或「已取消」 |

### 4.1 `MATCHED`/`ONGOING` 兩個分頁籤

**Tab 1「地點」**
- 活動地點投票區：未鎖定時顯示提案/投票/即時得票數（`propose_activity_location`/`vote_activity_location`）；鎖定後（`fn_start_activities` 已執行）顯示最終地點
- 集合地點欄：自由文字，任何成員可設定/修改（`update_meeting_point`，2 分鐘冷卻）
- 見面提示欄：個人化 30 字（`update_meeting_hint`），只顯示/編輯自己的那份

**Tab 2「成員」**
- 成員名單：頭像、顯示名稱、學制、科系、可信度等級小標籤
- 依 `source_request_id` 分組顯示「一起來的」（透過邀請連結加入的同一批人）
- 聯絡方式（點卡片展開，`get_activity_contacts`，24h 倒數 `contact_visible_until`；跟下面的「個人檔案卡」是兩個獨立入口，見下一點）
- 🟢 **個人檔案卡（v1.33）**：點成員頭像本身（跟點卡片其他區域展開聯絡方式是分開的獨立 tap target，互不影響）開啟一張唯讀的個人檔案卡——照片、顯示名稱、學校/科系/學制、自我介紹（`bio`，`get_activity_member_profiles` v1.33 新增）、可信度等級。`bio` 從 v1.33 起是註冊硬性門檻（見 SPEC.md v1.33），新使用者一定填過；既有使用者若還沒補，顯示「還沒有寫自我介紹」。
- 🟢 **封鎖／檢舉入口（v1.17/v1.18）**：點開成員卡片展開的選單裡，聯絡方式旁邊加「封鎖」「檢舉」兩個動作——這是使用者第一次真正知道對方身份的時機，適合作為主要入口。「封鎖」二次確認後呼叫 `blockUser()`，成功後只是安靜關閉選單（不告知「已封鎖」以外的額外資訊，畢竟對方永遠不會知道）；「檢舉」跳出小表單（分類下拉 SPAM/HARASSMENT/OTHER + 選填說明文字）呼叫 `submitReport()`。

**設計原則**：「地點」管去哪碰面（活動地點投票 + 集合地點），「成員」管跟誰碰面（含聯絡方式）。投票決定「去哪」跟填寫集合地點是兩個獨立的資料流、獨立 RPC，只在畫面上共用「地點」分類、用文案區分視覺呈現。

## 6. 三個突發彈窗

### 6.1 小人數安全確認（`PENDING_CONFIRMATION`）

- 顯示對方「安全資訊卡」：頭像、姓名、school、department、degree_level、可信度等級、已完成活動次數（**不含聯絡方式**）
- 倒數依 `confirm_window_expire_at` 動態計算（目前 `app_config.confirm_window_minutes`=10，但為可調參數，畫面不可寫死分鐘數）
- 動作：「確認參加」／「這次先不要」，10 分鐘內可反悔（重複呼叫覆寫）
- 逾時/拒絕後：顯示「此次配對未成立」，**不透露是誰、超時或拒絕**（對稱不歸因原則）
- 🟢 **封鎖／檢舉入口（v1.17/v1.18）**：安全資訊卡上也放同樣的「封鎖」「檢舉」兩個動作——低人數場景本來就是安全風險較高的情境，讓使用者在確認參加前就能先行封鎖/檢舉候選對象，不需要等到真正配對成立、進到第 4.1 節的成員名單才有這個選項。呼叫的 RPC 與行為跟第 4.1 節完全相同，只是入口提前。

### 6.2 人數調整同意（Downgrade）

- 顯示「目前只湊到 N 人，是否接受降到 {target_size} 人成局？」
- 倒數依 `downgrade_request.expire_at` 動態計算
- 動作：「同意」／「不同意」
- **給該 Request 所有已加入成員看，不是只給發起人**——每個成員看到的彈窗地位對等，需一致同意才成立，任一人不同意即否決

### 6.3 完成確認 + 再約（兩步）

**第一步：完成確認**
- 三選一：✅順利進行 ／ ❌對方沒來 ／ ⚪我自己取消了
- 選「對方沒來」時彈出該活動完整成員名單（不含自己），多選勾出未到場者 → `submit_completion_report(absent_user_ids)`
- 系統每 15 分鐘持續提醒（`COMPLETE_CONFIRMATION`）直到達法定人數門檻或 `start_time+24h` 自動結算

**第二步：再約（完成確認送出成功後緊接跳出）**
- 只列出第一步標記為「有順利進行」的成員
- 逐一可按「👍 再約」（`rematch_vote`），雙方都投才永久保留聯絡方式

## 7. 🔴 時段桶 UI（待細化）

方向已定案但尚未寫入實作細節：
- 5 個時段桶：早上(06-12)／中午(12-14)／下午(14-18)／傍晚(18-20)／晚上(20-24)，「現在」(30分鐘內)獨立為快速選項
- 動態顯示：僅列出起始時間落在 `now()~now()+24h` 內的桶；今天已過去的不顯示；跨越今日範圍的桶帶「明天」前綴
- 多選收斂：選取多個桶（含不連續）時，底層仍收斂為單一連續區間（最早選取桶的開始 ~ 最晚選取桶的結束），UI 需明確提示收斂後的實際範圍
- 詳細時間範圍模式：切換為直接選擇具體起訖時間，同樣受 24 小時上限約束

技術基礎已就緒：`create_request` 已改為直接接收 `p_earliest_start`/`p_latest_start` 原始時間戳（v1.16），前端可自由設計桶邏輯，無需再動 backend。

## 8. 我的 / 反饋QA

### 8.1 我的
- 個人資料卡：頭像、顯示名稱、學制、科系、自我介紹（可編輯）
- 性別欄位：折疊在個人資料卡「更多資料」內，不與頭像/名字平起平坐，文案提醒「僅供展示，不影響配對」
- 可信度等級徽章（Trusted/Normal/New）
- 聯絡方式（IG/LINE/Discord，至少一項）
- 帳號刪除入口：位置需明顯好找（Apple/Google 上架硬性規定），二次確認後呼叫 `deleteAccountFlow()`
- 反饋/QA 連結

### 8.2 反饋/QA 頁面內容（定案版）

Q1：為什麼沒有性別篩選？

這個 App 的核心理念是「找一起做事的人」，不是交友或約會軟體。我們刻意不讓性別成為配對條件，避免整個產品氣氛變成在配對象。你填的性別只會顯示在個人資料上，讓其他成員認識你，完全不會拿來篩選或決定要不要把你配給誰。

話雖如此，我們知道有些活動（例如夜間散步、單獨兩人的場合）確實有人會希望能限定同性別的夥伴，這是我們正在評估的方向（v2），如果你有這方面的需求或想法，歡迎透過下方信箱告訴我們。
2. **配對成功後，我要怎麼跟其他人聯繫？** 平台不提供站內聊天，透過對方公開的 IG/LINE/Discord 聯繫
3. **活動可以選科目/程度嗎（Matching Attributes）？** v2 評估中，視「讀書」等類型實際使用量決定，歡迎透過信箱回饋需求
4. **可以跨學校配對嗎？** 目前僅限同校（NYCU/NTHU 各自獨立），跨校功能評估中
Q5：這個 App 安全嗎？

安全性是我們最在意的事情之一，目前有這幾層機制：

身份驗證：只有 @nycu.edu.tw／@nthu.edu.tw 的學校信箱能註冊，確保你遇到的都是（曾經是）本校學生
盲配不挑人：配對成立前，系統不會讓任何人看到候選對象的個人資料，也不會有人能「挑」你或被你挑，降低被特定對象鎖定的風險
可信度制度：每個人依出席紀錄有 Trusted／Normal／New 三個等級，全新帳號無法直接參加只有兩人的活動，必須先完成過一次團體活動才能解鎖，避免陌生新帳號直接約你單獨見面
停權機制：連續多次放鳥（約好不出現）會被暫時停權
封鎖功能：如果遇到讓你不舒服的人，可以直接封鎖對方，之後系統不會再把你們配在一起，對方不會收到任何通知
帳號刪除：你可以隨時在「我的」頁面刪除帳號跟所有個人資料

我們無法做到絕對零風險——任何讓陌生人見面的服務都一樣——但這些機制的設計目標，就是把風險降到最低，並且讓你在感覺不對勁的第一時間，有實際能保護自己的工具，而不是只能默默忍受。
6. **怎麼確認大家都是在校學生？** 學校信箱驗證能確保曾是本校學生，但無法排除已畢業校友（部分學校畢業生信箱長期有效）；未來若能與校方系統整合會優先加上
7. 聯絡信箱

## 9. Notification 文案定案版

| 事件 | 標題 | 內文 |
|---|---|---|
| `MATCH_SUCCESS` | 配對成功！ | 你的活動已經成團，點開看看誰要一起去 |
| `ACTIVITY_UPCOMING` | 活動快開始了 | 還有 {lead_minutes} 分鐘，記得看一下活動地點跟集合地點 |
| `ACTIVITY_REMINDER` | 活動開始了 | 時間到囉，記得看一下活動地點跟集合地點再出發 |
| `LOCATION_NOT_YET_PROPOSED` | 還沒選活動地點喔 | 活動快開始了，還沒人提出活動地點，趕快去投一個吧 |
| `MEETING_POINT_UPDATED` | 集合地點更新了 | {display_name} 更新了集合地點：「{description}」 |
| `COMPLETE_CONFIRMATION` | 活動結束了嗎？ | 花 10 秒回報一下，這次有順利進行嗎？ |
| `DOWNGRADE_REQUEST` | 有人數調整需要你同意 | 目前人數不夠，是否同意降到 {target_size} 人成局？10 分鐘內沒回應視為不同意 |
| `DOWNGRADE_RESULT`（APPROVED） | 人數調整成立 | 活動改成 {target_size} 人進行囉 |
| `DOWNGRADE_RESULT`（REJECTED/TIMEOUT） | 人數調整沒有成立 | 活動維持原本的人數門檻，繼續幫你找人 |
| `MATCH_NOT_FORMED` | 這次配對沒有成立 | 別擔心，可以重新發起新的邀約，我們會繼續幫你找人 |

## 11. 新手上手引導（Onboarding）

### 11.1 首次登入跳出卡片（Onboarding，可跳過）

只在使用者第一次登入、且後端 `app_user.onboarding_seen_at` 為 null 時自動觸發，看過一次後不再自動跳出（可按叉叉關閉，關閉時呼叫更新 `onboarding_seen_at`）。內容依真實操作順序簡短預告接下來會發生什麼：

| 卡片 | 內容 |
|---|---|
| 1 | 選活動類型、時段、人數 → 送出，進入「等待室」 |
| 2 | 等待室可以邀朋友一起，也可以直接等系統幫你配對陌生人 |
| 3 | 配對成功（人數少時會先跳出安全確認）→ 進「我的活動」 |
| 4 | 活動確定後：一起投票決定去哪、填集合地點、填見面提示，方便認出彼此 |
| 5 | 活動結束：花 10 秒回報有沒有順利進行，可以跟一起參加的人按「再約」 |

**後端**：`app_user` 新增 `onboarding_seen_at timestamptz nullable`，選擇存後端而非純前端裝置記憶，理由是使用者換手機/重灌 App 是常見情境，只存本機會導致重複看到，體驗不佳。

### 11.2 常駐說明入口（比 Onboarding 詳細）

放在「我的」頁面或首頁右上角的說明圖示，隨時可查閱，內容比 Onboarding 更詳細、對應實際畫面的分步驟圖文說明，服務兩種情境：① 使用者用到一半忘記目前階段該做什麼；② 透過邀請連結加入、未必走過完整登入流程/看過 Onboarding 的新使用者。

## 12. 註冊流程：NYCU 在校生年限軟性提醒（v1.21）

出現時機：完善個人資料（`complete_profile`）畫面選完學制（`degree_level`）、按下「完成註冊」的當下——前端先呼叫 `checkEnrollmentReminder(degreeLevel)`，回傳 `true` 才跳出一次性確認彈窗，`false` 則直接送出、使用者無感。

- 文案大意：「提醒你，若已畢業，請注意在校生身份是本平台社群互信的基礎」
- 只有一個「我知道了，繼續」按鈕，**不提供「取消」**——即使判斷為已超過在校年限，使用者確認後仍照常完成註冊，不阻擋流程
- 只在這次註冊當下判斷一次，不會在之後的登入或使用過程中反覆跳出
- 僅 NYCU 帳號可能觸發（NTHU 這輪不做）；非 NYCU 帳號、或信箱格式無法解析出入學年，一律不觸發，使用者不會看到任何提示
